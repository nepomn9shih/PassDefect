# Руководство для AI-агентов: лучшие практики разработки (Phaser.js, React, TypeScript)

Данное руководство описывает стандарты и рекомендации для AI-агентов при работе с кодовой базой, использующей стек: **Phaser.js**, **React**, **TypeScript**, **styled-components**, **Redux Toolkit**.

Цель — повысить читаемость, поддерживаемость, расширяемость и производительность кода без изменения его функциональности.

---

## Общие принципы

- **Использовать TypeScript во всём коде**:
  - Все переменные, параметры функций, возвращаемые значения должны иметь типы.
  - Предпочитать `interface` или `type` для определения формата объектов.
  - Использовать `enum` для наборов констант, если уместно.
  - Включать строгую типизацию (`"strict": true` в `tsconfig.json`).

- **Синтаксис ES6+**:
  - Использовать `const`/`let` вместо `var`.
  - Использовать стрелочные функции, деструктуризацию, spread-операторы.
  - Использовать `import`/`export` вместо `require`.

- **Чистота кода**:
  - Избегать дублирования (DRY).
  - Уменьшать цикломатическую сложность: разбивать сложные функции на более мелкие.
  - Максимально упрощать логику условий.

- **Производительность**:
  - Минимизировать ререндеры в React.
  - Кэшировать вычисления (`useMemo`, `useCallback`).
  - Избегать лишних пересозданий объектов в рендере.

## React

### Хуки
- Использовать только хуки (функциональные компоненты), классовые компоненты **не использовать**.
- Правила:
  - `useState` — для локального состояния.
  - `useEffect` — с корректной зависимостью, избегать бесконечных циклов.
  - `useCallback` — оборачивать обработчики, передаваемые в дочерние компоненты.
  - `useMemo` — для тяжёлых вычислений.
  - `useRef` — для доступа к DOM или хранения мутабельных значений.
  - `useSelector` / `useDispatch` — из Redux Toolkit.
  - `useContext` — для доступа к глобальному состоянию, если не используется Redux.
  - `useReducer` — при сложной логике обновления состояния, особенно с вложенными объектами или несколькими связанными состояниями.
  - Создавать **кастомные хуки** (например, `useWindowSize`, `useGameControls`, `usePhaserEvent`) для извлечения и повторного использования логики между компонентами.

### Структура компонентов
- Именование: `PascalCase` для файлов и компонентов.
- Файловая структура: `components/Button/index.tsx`, `components/Button/styles.ts`.
- Разделять логику и UI: использовать кастомные хуки (`hooks/useGameLogic.ts`).
- Организовывать компоненты по признаку: `ui` (кнопки, индикаторы), `layout` (сетки, контейнеры), `features` (игровые элементы, панели управления).
- Использовать `index.ts` в папках компонентов для удобного импорта.
- Избегать компонентов с множественной ответственностью — один компонент = одна задача.
- Выносить тяжёлые JSX-деревья в отдельные компоненты, даже если они используются один раз.

### styled-components
- Использовать `styled-components` для стилизации.
- Выносить стили в отдельные файлы: `styles.ts`.
- Использовать темы (`ThemeProvider`) для единого стиля.
- Избегать инлайн-стилей.
- Определять пропсы в `styled`-компонентах с использованием TypeScript-интерфейсов.
- Использовать `as` и `forwardedAs` для корректного рендеринга HTML-тегов.
- Избегать вложенности более чем на 2 уровня — это ухудшает производительность и читаемость.

## Phaser.js

### Структура игры
- Разделять игру на сцены: `BootScene`, `MainScene`, `GameOverScene` и т.д.
- Каждая сцена — отдельный класс, реализующий `Phaser.Scene`.
- Использовать TypeScript-интерфейсы для типизации сцен и объектов.
- Использовать `ScenePlugin.launch()` и `ScenePlugin.stop()` для явного управления жизненным циклом сцен.
- Передавать зависимости между сценами через события (`this.events.emit`) или общий `store` (Redux), а не через глобальные переменные.
- Использовать `init()`, `preload()`, `create()`, `update()` согласно фазам жизненного цикла Phaser.
- **Для игр со спавном монстров использовать `MainScene` как основную сцену с автоматическим спавном врагов и предметов**, организованным через `Spawner`-классы с настраиваемыми интервалами и волнами.
- **Выносить общую логику сцен в базовые классы или миксины**, если используется несколько похожих сцен (например, `BaseGameScene` с общей камерой, UI, управлением).
- **Использовать `scene.sleep()` и `scene.wake()` для приостановки сцен без их полной остановки**, например, при открытии паузы.
- **Организовывать управление сценами через `SceneManager` или центральный `GameManager`**, а не напрямую из React.

### Ресурсы
- Загружать ресурсы в `preload()`.
- Использовать атласы (`atlas`, `spritesheet`) для оптимизации.
- Централизованно управлять путями к ассетам.
- Использовать `this.load.setPath()` для группировки загрузки ресурсов.
- Использовать `this.load.on('progress', ...)` и `this.load.on('complete', ...)` для отображения прогресса загрузки.
- Освобождать ресурсы через `this.scene.scene.keys[sceneKey].cache` и `this.textures.remove(key)` при смене сцены, если не нужны глобально.
- **Для игр с большим количеством ассетов реализовать поэтапную загрузку**: сначала UI и звук, потом карты и персонажи.
- **Использовать `this.load.image()`, `this.load.spritesheet()`, `this.load.audio()` с явным указанием ключей**, избегать динамических имён.
- **Выносить все ключи ассетов в `enums` или константы**, чтобы избежать опечаток и упростить рефакторинг.
- **Использовать `this.cache` для хранения не-графических данных**, таких как конфигурации предметов, параметры врагов, волны спавна.
- **Применять `Phaser.Loader` плагины при необходимости** (например, для загрузки JSON-схем, шрифтов, шейдеров).

### Производительность
- Использовать `container`, `group` для управления объектами.
- Дебажить производительность через `Phaser.Debug`.
- Избегать создания объектов в `update()`.
- Использовать `getFirstDead()` и переиспользование объектов вместо постоянного создания/уничтожения.
- Оптимизировать коллизии: группировать статические объекты в `StaticGroup`, использовать `overlap` только при необходимости.
- Использовать `setVelocity` вместо прямого изменения `x`/`y` для физических объектов.
- Минимизировать вызовы `setFrame`, `setTexture`, `setDepth` — кэшировать значения при частом использовании.
- Использовать `Phaser.Math.Distance.Between` и `Phaser.Math.Angle.Between` для оптимизированных вычислений.
- Выносить тяжёлые операции (например, поиск пути) в отдельные таймеры или воркеры, если возможно.
- **Заменить `setInterval`/`setTimeout` на `this.time.addEvent()`** — встроенный таймер Phaser, интегрированный с игровым циклом, безопасный при паузе/остановке сцены.
- **Использовать `this.time.delayedCall()` вместо `setTimeout(..., 0)`** — обеспечивает синхронизацию с кадрами и корректную работу при изменениях скорости игры.
- **Оптимизировать частоту обновлений AI монстров** — не обновлять каждый кадр, а использовать таймеры (например, раз в 500–1000 мс), особенно для игр в стиле Vampire Survivors с большим количеством врагов.
- **Упрощать логику `update()`** — выносить нетребовательные к частоте обновления операции в отдельные методы с таймерами.
- **Использовать `Phaser.Utils.Array.GetRandom()` для эффективного выбора случайных элементов.**

### Интеграция с React
- Использовать `ref` для монтирования `Phaser.Game`.
- Управлять жизненным циклом игры через `useEffect`.
- Передавать состояние из React в Phaser через пропсы или контекст.
- Использовать `useCallback` для передачи колбэков в Phaser-сцены.
- Избегать прямого доступа к React-состоянию из Phaser: использовать `store.subscribe()` или события.
- Добавлять `Phaser.Game` в `useRef` для предотвращения пересоздания при ререндерах.
- Очищать подписки и таймеры в `useEffect.cleanup`.
- **Создавать тонкий слой абстракции (`PhaserGameComponent`) для инкапсуляции Phaser-логики**, чтобы React не ререндерил игру.
- **Использовать `React.memo` для компонентов UI, показывающих игровое состояние**, чтобы избежать лишних обновлений.
- **Передавать только необходимое состояние из Redux в Phaser**, а не полный store.
- **Использовать `useSelector` с селекторами, мемоизированными через `reselect`**, чтобы минимизировать рекомпиляцию.
- **Организовывать взаимодействие через события** (`GameEvents`) — Phaser излучает события, React-компоненты их слушают, и наоборот.

## Тестирование

### Общие принципы
- Писать unit-тесты для хуков, утилит, слайсов.
- Использовать `React Testing Library`, `Jest`.
- Покрывать критическую логику тестами.
- Писать тесты, которые тестируют поведение, а не реализацию.
- Избегать тестирования приватных деталей реализации компонентов.
- Предпочитать `screen.getByRole`, `screen.getByLabelText`, `screen.getByText` для поиска элементов.
- Использовать `data-testid` только тогда, когда семантические методы поиска неприменимы.
- Организовывать тесты по принципу Given-When-Then (или Arrange-Act-Assert).
- Использовать `describe` блоки для группировки тестов по функциональности.
- Изолировать тесты — каждый тест должен быть независимым.
- Размещай тесты в папке `tests` внутри папки с тестируемым компонентом (например, `components/Button/tests/Button.test.tsx`).
- Использовать `jest.fn()` и `jest.mock()`, а не `vi.fn()` или `vi.mock()`, поскольку проект использует Jest, а не Vitest.

### React Testing Library: лучшие практики
- Всегда использовать `render` компонента внутри `describe` или `test`.
- Использовать `render` с `wrapper`, если компоненту нужны контекст или провайдеры (например, Redux, ThemeProvider).
- Использовать `userEvent` вместо `fireEvent` для симуляции пользовательских действий — он более точно имитирует реальное поведение браузера.
- Импортировать `userEvent` напрямую:
  ```ts
  import { userEvent } from '@testing-library/user-event';
  ```
- Использовать асинхронные утилиты (`findBy*`, `waitFor`) при тестировании асинхронных операций.
- Не использовать `waitFor` без таймаута или условия — это может привести к хрупким тестам.
- Использовать `waitForElementToBeRemoved` для ожидания исчезновения элементов (например, спиннеров).
- Очищать состояние после тестов с помощью `afterEach(cleanup)` — хотя это часто делается автоматически.
- Использовать `jest.mock()` для мокирования внешних зависимостей (API, хуков, модулей).
- Применять `vi.mock()` при использовании Vite/Jest с `vitest`.
- Покрывать крайние случаи: загрузка, ошибки, пустые состояния.
- Тестировать обработку пользовательского ввода и валидацию форм.
- Проверять, что события корректно вызываются и передают правильные аргументы.
- Использовать `expect` с соответствующими матчерами из `@testing-library/jest-dom`:
  - `toBeDisabled`, `toBeEnabled`
  - `toBeVisible`
  - `toHaveFocus`
  - `toHaveTextContent`
  - `toHaveClass`
  - `toBeInTheDocument`
- Избегать излишнего количества тестов, проверяющих одну и ту же логику.
- Поддерживать тесты в актуальном состоянии при изменении компонентов.

## Работа AI-агента

При внесении изменений AI-агент должен:

1. **Анализировать контекст** перед редактированием.
2. **Разбивать сложные функции** на более мелкие.
3. **Устранять дублирование** через вынесение в утилиты или хуки.
4. **Типизировать всё**, что не типизировано.
5. **Использовать хуки React** вместо классов.
6. **Оптимизировать ререндеры** через `React.memo`, `useCallback`, `useMemo`.
7. **Следить за производительностью** Phaser (не создавать объекты в `update`).
8. **Сохранять функциональность** — не менять поведение приложения.
9. **Форматировать код** согласно `eslint` и `prettier`.
10. **Проверять, что новые компоненты и хуки имеют минимальную зависимость от внешних данных**, используют пропсы и колбэки.
11. **Избегать возврата `null` из компонентов** — использовать `return <></>`, `return false` или условный рендеринг.
12. **Предпочитать функциональные компоненты с деструктуризацией пропсов**:
    ```tsx
    const Button = ({ onClick, children }: Props) => {
      return <button onClick={onClick}>{children}</button>;
    };
    ```
13. **Не использовать индексы массива как `key` в `map()`**, только уникальные идентификаторы.

> ⚠️ **Важно**: AI-агент не должен вносить изменения, выходящие за рамки текущей задачи. Все изменения должны быть минимально инвазивными и целенаправленными.
