# Поднятие версии и CHANGELOG

## Контекст проекта

- Версия живёт в одном месте: `package.json` (`"version"`).
- История изменений — `CHANGELOG.md` в корне репозитория, формат Keep a Changelog, описания на русском.
- Эталон формата — секция `1.1.0` в `CHANGELOG.md`.

## Когда применять

- Пользователь просит поднять версию, сделать релиз, задокументировать изменения с прошлой версии.
- Не применять для промежуточных правок без запроса пользователя.

## Порядок действий

1. **Определи текущее состояние**: прочитай `"version"` в `package.json` и последнюю секцию `## X.Y.Z` в `CHANGELOG.md`.
2. **Собери изменения с прошлой версии**:
   - посмотри `git log --oneline` и `git status`/`git diff` (правки могут быть не закоммичены);
   - дополни из контекста сессии, если правки делались в этом чате;
   - не выдумывай пункты: каждая запись должна подтверждаться диффом, коммитом или явным обсуждением.
3. **Определи тип бампа** (semver):
   - `patch` (1.1.0 → 1.1.1) — только фиксы багов и чистка;
   - `minor` (1.1.0 → 1.2.0) — новая функциональность, фичи;
   - `major` (1.1.0 → 2.0.0) — ломающие изменения механики, API, стейта.
   - Если тип неочевиден или пользователь не указал — уточни вопросом с вариантами.
4. **Обнови версию** в `package.json`.
5. **Добавь секцию в ВЕРХ `CHANGELOG.md`** (под заголовком, перед предыдущей версией):
   - заголовок `## X.Y.Z — YYYY-MM-DD` с реальной датой дня;
   - короткое вступление 1–2 предложения о сути релиза (что и зачем);
   - группы `### Added`, `### Fixed`, `### Changed` — используй только непустые;
   - каждый пункт — одна строка: суть + следствие. Пиши конкретно («появились утечки» → «устранены утечки»), без канцеляризмов и воды.
6. **Ничего не коммить и не пушить автоматически** — коммит только по явной просьбе пользователя.
7. **Покажи итог**: старая → новая версия и список групп новой секции.

## Формат записи (эталон)

```markdown
## 1.2.0 — 2026-11-05

Короткое вступление о сути релиза.

### Added

- Что нового и что это даёт.

### Fixed

- Какой баг исправлен и чем это грозило раньше.

### Changed

- Что переработано и как стало лучше.
```

## Чего не делать

- Не описывать в CHANGELOG внутренние шаги работы агента, метаправки скиллов и служебные файлы (`.opencode/`), если пользователь явно не попросил.
- Не пропускать шаг сбора изменений из git — «по памяти» легко потерять правки.
- Не начинать секцию с «Обновление проекта», «Разные исправления» — только конкретика.
